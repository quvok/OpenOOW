# Архитектура OpenOOW

Документ фиксирует границы модулей по Технической спецификации 1.0. Это целевая архитектура; наличие пункта в документе не означает, что модуль уже реализован.

## Правила зависимостей

- `src/core/**` — расчётное ядро на TypeScript. Не импортирует React, DOM, Canvas, Three.js, IndexedDB или код UI.
- `src/ui/**` — интерфейс и визуализация. Может вызывать публичные функции ядра, но не содержит навигационных расчётов.
- `src/adapters/**` (по мере появления) — адаптеры браузера, хранения и платформы.
- `tests/**` — проверка расчётного ядра и интеграций. Расчётные тесты не должны зависеть от браузерного окружения.

## Целевые подсистемы

| Подсистема | Предполагаемая ответственность |
|---|---|
| Simulation Engine | Фиксированный шаг, порядок обновления подсистем, воспроизводимость |
| Ship Dynamics | Поступательное движение, курс, рыскание, рулевой привод, движитель |
| Environment Model | Ветер, течение, волнение, видимость |
| Navigation Instruments | Компас, лаг, эхолот и модели погрешностей |
| Radar Processing | Отражения/цели, дальность, пеленг, clutter и режимы отображения |
| ARPA Tracking | Захват, фильтрация, сопровождение, векторы, CPA/TCPA и тревоги |
| COLREG Assessment | Контекст ситуации, применимые правила, оценка действий и объяснение |
| Scenario Engine | Начальные условия, трафик, события и воспроизводимые сценарии |
| Examination Engine | Критерии, журнал событий, оценка и разбор |
| UI | Органы управления, приборы, 2D/3D представление |

## Единицы и координаты

- Плоская локальная система: East/North, морские мили (NM).
- Скорость: узлы (kn), то есть NM/hour.
- Истинный курс и пеленг: градусы по часовой стрелке от истинного севера, диапазон нормализуется к [0, 360).
- Время ядра: секунды.
- Угловая скорость: градусы в секунду; для индикации ROT может отображаться в градусах в минуту.
- Положительный угол руля в текущей модели означает правый борт.

Для больших географических областей локальная плоская система не подходит: геодезическая модель координат будет отдельным решением.

## Фиксированный шаг и воспроизводимость

Ядро получает явный `dtSeconds`; текущий шаг прототипа равен 0,1 с. Интерфейс использует `requestAnimationFrame` только как источник прошедшего реального времени. Накопитель времени передаёт в `advanceFixedSteps` только целые фиксированные шаги. Остаток времени сохраняется между кадрами, а ограничение числа шагов за один вызов не отбрасывает накопленный остаток.

Simulation Engine находится в `src/core/simulationEngine.ts` и не зависит от React или браузерных API. Цикл UI хранит состояние симуляции отдельно от React state; React state используется для отображения. При одинаковом начальном состоянии, последовательности команд и фиксированном шаге расчётное ядро должно воспроизводить одинаковую последовательность состояний.

## Текущая реализация и ограничения

- Реализована упрощённая модель одного судна в `src/core/shipDynamics.ts`.
- UI подключает модель через фиксированный Simulation Engine; в React-компоненте остаются только команды и отображение.
- Движение целей по постоянным курсам и скоростям использует `advanceVessel` из `src/core/navigation.ts`.
- UI обновляет собственное судно и трафик одинаковым фиксированным шагом; CPA/TCPA пересчитываются по текущим состояниям.
- Этот расчёт остаётся кинематическим прогнозом при неизменных векторах и не является ARPA-сопровождением.
- Текущий интерфейс — 2D прототип, не 3D-мостик и не сертифицированный прибор.
- Радарный North-Up PPI держит собственное судно в центре; измеренные контакты проецируются относительно координат собственного судна через `src/core/radar.ts`. PPI обновляет отметки по обзорам, а не на каждом fixed step.
- Векторы отображаются для заданного времени (сейчас 6 минут) в двух режимах: истинный — по оценённой скорости/курсу цели, относительный — по разности оценённой скорости цели и скорости собственного судна. До появления оценки ARPA вектор не рисуется.
- Модель радиолокационных измерений реализована в `src/core/radarMeasurements.ts`: обзор каждые 2,5 секунды симуляционного времени; измерение дальности и истинного пеленга без искусственной погрешности и без искусственных пропусков в стандартном режиме; ограничение дальности 3 NM. Период обзора сохраняет дискретное обновление отметок, но все цели в пределах дальности обнаруживаются на каждом обзоре. Настраиваемые погрешности могут быть добавлены позднее отдельным режимом, а не навязываться базовому сценарию.
- ARPA-ядро реализовано в `src/core/arpa.ts`: ручной захват начинает измерительную историю с PPI-отметки; скорость и курс оцениваются линейной регрессией по последним восьми завершённым радиолокационным измерениям. Сценарные курс/скорость цели не используются для оценки.
- Состояния ARPA: `acquiring` после первого измерения, `tracking` после получения оценки скорости, `lost` после трёх пропущенных обзоров (7,5 с при периоде 2,5 с). При повторном появлении последней ассоциированной отметки история сбрасывается.
- Target Swap: активные треки прогнозируют положение на время нового обзора; пары «трек–отметка» сортируются по дистанции, затем выполняется взаимно-однозначное назначение в пределах 0,05 NM. Если отметка меняет ассоциацию, логический ID трека сохраняется, `associatedRadarId` обновляется, а событие и счётчик swap фиксируются. Это детерминированная учебная ассоциация, не гарантирующая безошибочную идентификацию в плотном трафике.
- CPA/TCPA вычисляются по измеренному положению, оценённой скорости цели и текущей скорости/курсу собственного судна. Вектор True использует оценённый вектор цели; Relative вычитает вектор собственного судна. Длительность отображаемого вектора настраивается от 1 до 30 минут.
- Trial Manoeuvre рассчитывает отдельное решение CPA/TCPA для пробных курса и скорости собственного судна. Состояние симуляции и фактические органы управления не меняются. Это кинематический прогноз без модели динамики поворота/торможения.
- Учебная тревога опасного сближения активна только для `tracking`, положительного TCPA в заданном окне и DCPA ниже настроенного порога; стандартные значения — DCPA 0,5 NM и TCPA до 15 минут. Это не норматив COLREG.
- История радиолокационных следов реализована в `src/core/radarTracks.ts`: начальная точка создаётся по первому измеренному обзору; новые точки добавляются только для фактически обнаруженных отметок после каждого сканирования (2,5 с); хранится максимум 240 точек на цель (~10 минут). Пропуски обзора не создают фиктивных точек; при сбросе сценария история очищается.
- При записи сохраняется измеренное относительное положение отметки к собственному судну на момент обзора; это не позволяет движению собственного судна задним числом смещать старые точки. UI отображает эти измеренные координаты в North-Up PPI; точки вне радиуса не рисуются. След является дискретной историей радиолокационных отметок, а не сглаженным ARPA-треком.
- Ручные EBL/VRM-оверлеи привязаны к центру собственного судна. Выбранная отметка PPI показывает измеренные дальность и истинный пеленг, разницу с настройками EBL/VRM и предоставляет действие ручного захвата ARPA. Выбор работает мышью, касанием и клавиатурой.
- Параметры динамики — допущения, а не паспортные или испытательные характеристики реального судна.
- Ветер, течение, волны, движитель, реверс, боковой снос, датчики, физическая модель радара, автоматический захват новых целей и полноценное сертифицированное ARPA/COLREG пока не реализованы. ARPA — учебная модель ассоциации и сопровождения измеренных отметок, а не замена судового оборудования.

## Правило добавления подсистемы

Новая подсистема сначала получает документированные входы/выходы, единицы, допущения и тесты в `src/core`. После этого UI подключает её через публичный API. Нельзя помещать бизнес-логику в React-компоненты или маскировать отсутствующие данные визуальными значениями.
